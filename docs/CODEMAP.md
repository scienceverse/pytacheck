# Code map

This page is for people who know metacheck's R code and want to find where each
part of it lives in this Python port, and how closely it follows R. It maps every
check (module), every exported R function and every R package dependency to its
Python location. It is a navigation aid. The reasons behind the design are in
[ARCHITECTURE.md](ARCHITECTURE.md) and [PORTING.md](PORTING.md).

The tables are generated by [`scripts/codemap.py`](../scripts/codemap.py) from the
files the port keeps up to date anyway, so they follow the code. The test suite
fails when this page falls behind (run `uv run python scripts/codemap.py` to
refresh it). The prose, the package table and the data section are written by hand.

## How the Python package is laid out

The distribution is called `metacheck` on PyPI and the import package is
`metacheck`, in [`src/metacheck`](../src/metacheck). (The project started as
"pytacheck"; `import pytacheck` and the `pytacheck` command still work, through the
small alias package in [`src/pytacheck`](../src/pytacheck).)

Most R files map to one Python file, grouped into subpackages by topic:

|---|---|---|

| `papers/` | `Paper` and `PaperList` (bibr export schema 12.0, and the older format), reading and writing papers, cross-paper tables, validation. | `R/paper.R`, `R/import-read.R` |

A few top-level files hold shared pieces: [`module.py`](../src/metacheck/module.py)
(the module system: `module_run()`, `module_list()`, `module_help()`, from
`R/module.R`), [`config.py`](../src/metacheck/config.py) (options and folders, from
`R/zzz.R` and `R/utils.R`), [`utils.py`](../src/metacheck/utils.py) (messages,
progress bars and small helpers, from `R/utils.R` and `R/svutils-*.R`),
[`log.py`](../src/metacheck/log.py) (`R/utils-logging.R`),
[`validate.py`](../src/metacheck/validate.py) (`R/validate.R`) and
[`http.py`](../src/metacheck/http.py) (one shared HTTP client with metacheck's
retry and rate-limit rules). [`cli.py`](../src/metacheck/cli.py) (the command
line), [`presets.py`](../src/metacheck/presets.py),
[`provenance.py`](../src/metacheck/provenance.py) (run records) and
[`status.py`](../src/metacheck/status.py) (validation labels) have no R
counterpart.

**R conventions: `_r/`.** Python does not share some R behaviour that users can
see. [`src/metacheck/_r`](../src/metacheck/_r) keeps it in one place:
[`regex.py`](../src/metacheck/_r/regex.py) runs metacheck's regular expressions
(TRE and PCRE syntax, R's replacement syntax and R's empty-match rules) on the
Python `regex` engine; [`base.py`](../src/metacheck/_r/base.py) has R's number
formatting (`as.character()`, `format()`), `round()` and `signif()`, `paste()`,
`trimws()` and R's string collation; [`frames.py`](../src/metacheck/_r/frames.py)
has the two dplyr verbs (`bind_rows()`, `count()`) whose pandas equivalents give a
different table. Where a pattern or an engine differs from R on purpose, the
entry is D29 in [UPSTREAM_ISSUES.md](UPSTREAM_ISSUES.md). The translation rules
are in [PORTING.md](PORTING.md), section 3.

## How parity with R is tested

Every change is checked against metacheck itself, run in R
([PARITY.md](PARITY.md) has the details):

* [`parity/cases`](../parity/cases) lists what to run, one file per **area** (a
  topic such as `db`, `mod_coi` or `bibr12`): an R function or a module, and its
  arguments. A `<area>_review` file next to it holds further edge cases.
* [`parity/golden`](../parity/golden) holds R's results for each case, recorded by
  running metacheck. Python's results are compared with them value by value,
  within small margins (exact counts and traffic lights, numbers to a relative
  1e-9, text after whitespace normalisation).
* Where Python differs from R on purpose, the case carries a **mark** that gives the
  reason, either in the case file or in [`parity/divergences`](../parity/divergences).
  Each mark cites an entry of [UPSTREAM_ISSUES.md](UPSTREAM_ISSUES.md), the register
  of differences: **U-entries** are bugs in metacheck (or its dependencies) that
  the port fixes or keeps, **D-entries** are deliberate design differences.
* The port does not copy R bug for bug. It aims to be at least as accurate as
  metacheck on real inputs ([PORTING.md](PORTING.md), section 1).

[STATUS.md](STATUS.md) has the overall numbers: how much is ported, and how many
parity cases pass in each area.

## Reading the tables

* **Python locations** are written `module:name`, for example
  `metacheck.db.doi:doi_clean` means `from metacheck.db.doi import doi_clean`. The
  link goes to the file that defines it. Public functions can also be imported from
  the top level (`metacheck.doi_clean`).
* **Names.** An R name becomes a Python name by a fixed rule: dots become
  underscores, and an internal `.name` becomes `_name`. A "Python name differs"
  note marks the functions that break this rule.
* **Parity** says whether at least one parity case calls the R function directly.
  "—" does not mean untested: the function may be covered through the modules or
  functions that use it, and by the Python tests.
* **Recorded differences** (in the module table) and **Differences** (in the
  function tables) list the register entries that the marks on those parity cases
  cite. Look them up in [UPSTREAM_ISSUES.md](UPSTREAM_ISSUES.md). "—" means that
  no parity case of that function or check cites an entry. Marks of the two kinds
  that cite none are not counted: quirks of R's C libraries on malformed or
  synthetic input, and R type details users do not see ([PARITY.md](PARITY.md)).
* **Status** is the validation label of a check, from the status snapshot
  [`resources/status/validation.json`](../src/metacheck/resources/status/validation.json).
  The snapshot is provisional: until the metacheck team keeps its own registry,
  "validated" means that the R module's `<validation>` block reports counts, not
  that the Python port was validated separately.
* **Tests** are the folders under [`tests`](../tests) whose tests exercise the
  check. Each folder is named after the area that owns the R file. "—" means
  that no test file there names the check; its parity cases still run it.
* Internal R functions (not exported) are not listed here.
  [`porting/symbols.json`](../porting/symbols.json) maps every R function,
  internal ones included, to its Python home, and the files in
  [`porting/map`](../porting/map) map each R file to its Python files.
